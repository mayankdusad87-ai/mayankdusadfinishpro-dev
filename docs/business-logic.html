resolveStatus() — runtime status derivation

The database stores the user-chosen status (e.g. in_progress). At read time, resolveStatus(userStatus, expectedEnd) derives the display status by comparing the expected end date against today:

User StatusExpected End Passed?Resolved Status
in_progressYesin_progress_delayed
not_startedYesdelayed
completedYescompleted_delayed
AnyNo / missingUnchanged
Why this matters The _delayed variants are never stored directly by user action — they are computed dynamically. This means overdue status is always current as dates pass, without requiring batch updates.

Filter dropdown — "Delayed" removed

The filter dropdowns (admin + supervisor) show: All Statuses, Not Started, In Progress, Completed, On Hold. "Delayed" was removed from the filter because delayed status is a computed derivative of in_progress or not_started + overdue date — exposing it as a separate filter caused confusion.

Status Rank (used for reversal detection)

Each status has a rank number. A status change where the old rank is higher than the new rank is a "reversal" — going backwards.

StatusRank
On Hold-1 (exempt from reversal checks)
Not Started0
In Progress / In Progress Delayed1
Completed / Completed Delayed2
Example Changing from Completed (rank 2) to In Progress (rank 1) is a reversal. Changing from On Hold (rank -1) to anything is NOT a reversal — On Hold is exempt.

Delay & On-Hold Reason Logic

When is a reason required?

When a supervisor changes an activity status to Delayed or On Hold, they must select a reason from a dropdown. The dropdown is populated from admin-configured reasons.

"Others" option

The dropdown includes an "Others" option. When selected:

  • The remarks text field becomes mandatory
  • On save, the free-text remarks value is stored as the delay_reason (not the word "Others")
Example Supervisor selects "Others" and types "Lift not working, material stuck on ground floor." This text is stored as the delay reason, not "Others."

Reason configuration (Admin)

Admins can create, edit, reorder, and deactivate reasons from Settings. Supervisors only see reasons marked as is_active = true. Deactivating a reason does not change activities that already use it.

Date Handling & Validation

Four types of dates

Date TypeSet ByPurpose
Expected Start / EndAdmin (from Excel or inline edit)The original planned schedule
Revised Start / EndAdmin (inline edit or bulk update)Updated schedule when plans change
Actual Start / EndSupervisor (on status change)When work actually happened

Validation rules

  • Actual start cannot be in the future. Error: "Actual start date cannot be a future date."
  • Actual end cannot be before actual start. Error: "Actual end date cannot be earlier than actual start date."

Auto-population rules

ActionWhat happens
Quick "Start" buttonactual_start = today, status → in_progress
Quick "Complete" buttonactual_end = today. If actual_start is empty, it's also set to today.
Trying to complete without actual_startDetail sheet opens with error: "Please enter the Actual Start date before marking as completed."

Reversal date-clearing rule

When an activity is reverted to not_started (a reversal), both actual_start and actual_end are automatically cleared (set to null). This ensures the activity's dates are clean for when work restarts.

v2.0 Addition Previously, reverting to not_started would leave stale actual dates in the database. The activity engine now explicitly clears them so downstream calculations (overdue, health score, projections) are not polluted.

Overdue Calculation

An activity is considered overdue when:

  • Its status is NOT completed
  • Its expected_end date has passed (is before today)
Days Overdue = floor( (Today − Expected End) / 86,400,000 )
Result in whole days. Only calculated when expected_end exists and is before today.

Supervisor priority categories

CategoryCondition
OverdueNot completed AND expected_end < today. Sorted by most overdue first.
Due TodayNot completed AND expected_end = today
Starting TodayStatus is not_started AND expected_start = today
Done TodayStatus is completed AND actual_end = today
07

Audit Trail & Reversal Detection

What is logged

Every status change creates an audit log entry capturing:

  • Activity ID, Project ID
  • Who made the change (user ID → resolved to name and role)
  • Old status → New status
  • Floor, Flat number, Stage, Sub-stage, Activity name
  • Timestamp

Audit entries are only created when the old status is different from the new status.

Reversal detection & notification

A reversal is when an activity moves backwards in the workflow:

  • Completed → In Progress (rank 2 → 1) = REVERSAL
  • Completed → Not Started (rank 2 → 0) = REVERSAL
  • In Progress → Not Started (rank 1 → 0) = REVERSAL
  • Any → On Hold = NOT a reversal (On Hold is exempt)
  • On Hold → Any = NOT a reversal (On Hold is exempt)

When a reversal is detected, two things happen:

  1. Email notification — Sent to all admin email addresses via the Resend API. Includes project name, floor, flat, activity details, and old/new statuses.
  2. In-app notification — Created for all active admin users. Shows as a bell icon alert with type reversal, title "Status Reversal — Floor X, Flat Y", and detailed message.
v2.0 Addition Previously, reversals only sent an email. Now they also create in-app notifications visible in the admin bell icon dropdown. See Section 14 for the full notification system.

Project Health Score Formula

The Health Score is a single number (0–100) displayed on the admin dashboard. It combines three factors:

Health Score = (Progress × 0.4) + (On-Time × 0.3) + (Low Risk × 0.3)
Rounded to nearest integer

Component definitions

ComponentFormulaWhat it measures
Progress (40%)(completed + completed_delayed) / total × 100How much work is done overall
On-Time (30%)completed / (completed + completed_delayed) × 100Of finished work, how much was on time
Low Risk (30%)100 − ((in_progress_delayed + on_hold) / total × 100)How little work is at risk

Activities with status not_applicable are excluded from the total count.

Score thresholds

Score RangeLabelColor
80–100HealthyGREEN
60–79Needs AttentionYELLOW
40–59At RiskORANGE
0–39CriticalRED
Example A project with 1000 activities: 400 completed (350 on-time, 50 delayed), 100 in_progress_delayed, 50 on_hold, 450 other.

Progress = 400/1000 × 100 = 40
On-Time = 350/400 × 100 = 87.5
Low Risk = 100 − (150/1000 × 100) = 85
Score = (40 × 0.4) + (87.5 × 0.3) + (85 × 0.3) = 16 + 26.25 + 25.5 = 68 → "Needs Attention"

Floor Heatmap & Rollup Logic

The admin dashboard heatmap shows completion status using a 4-level rollup, from individual activities up to floor readiness.

Level 1: Activities → Sub-stage

Group all activities by flat + stage + stage_gate (sub-stage). Count completed and total. A sub-stage is:

  • Completed — all activities completed
  • Running — some activities in progress or completed, not all
  • Yet to Start — all activities are not_started

Level 2: Sub-stages → Flat's Stage

For each flat, roll up all sub-stages within a stage. Same logic: all completed = Completed, none started = Yet to Start, otherwise = Running.

Level 3: Flats → Floor's Stage

For each floor, roll up all flats within a stage. Count how many flats have completed the stage vs total.

Level 4: Floor Readiness

ReadinessCondition
CompletedAll stages for this floor are completed
RunningAt least one stage has started
Not ReadyNo stage has started

Hardcoded Stage Order

Stages are displayed in this fixed order on the heatmap:

  1. Pre-Tiling
  2. Tiling
  3. Post Tiling
  4. Pre Paint Activities
  5. 1st Coat Paint
  6. Post First Coat Paint
  7. Second Coat Paint
  8. Post Second Coat Paint
  9. Lobby Flooring

Any stage not in this list sorts to the end.

Bulk Update Rules

Supervisor bulk updates

  • Only available in Floor view or when a Stage filter is applied in All Floors view
  • Two actions: "Start All" and "Complete All"
  • Activities already marked Completed are skipped
  • "Start" sets actual_start = today, status → in_progress
  • "Complete" sets actual_end = today; if actual_start is missing, also sets it to today
  • Each activity is updated individually with full audit trail
  • On mobile: bulk updates are restricted (limited functionality)

Admin bulk updates

  • Vendor reassignment: updates all selected rows with a new vendor name
  • Date update: can update any combination of expected_start, expected_end, revised_start, revised_end. Blank fields keep existing values.
  • Admin bulk updates do NOT create audit log entries (they use bulkUpdateActivities, not updateActivityWithAudit)

Refuge Floor & Unit Logic

Certain floors and units are designated as "refuge" (fire safety / structural). These are configured per project by the admin.

  • Refuge floors and units are stored as integer arrays on the projects table
  • In the Activity Table, refuge rows get an amber background and an "R" badge
  • A row is refuge if its floor is in refuge_floors OR its flat number is in refuge_units

Authentication & Session Management

Idle timeout

Sessions automatically expire after 1 hour of inactivity. Activity is detected via mouse, keyboard, touch, and scroll events. On timeout, the user is signed out and redirected to the login page.

Tab visibility check

When the user switches back to the app's browser tab, the session is re-validated. If expired, the user is silently signed out.

Account deactivation (Supervisor & Management)

When an admin deactivates a supervisor or management user:

  • is_active is set to false in the profiles table
  • A ban of ~100 years (876000h) is applied in Supabase Auth
  • Reactivation reverses both: is_active = true and ban duration set to none
  • An email notification is sent to the user's email address (see Section 15)

Password requirements

Minimum 6 characters. Enforced by Zod validation on the API route.

Login error messages

Error TypeUser-Facing Message
Invalid credentials"Incorrect email or password."
Email not confirmed"Please verify your email before signing in."
Rate limited"Too many login attempts. Please wait a moment."
Deactivated account"Your account has been deactivated. Please contact your administrator."
Other errors"Unable to sign in. Please try again."
v2.0 Addition Previously, Supabase's raw "User is banned (400)" error was shown to deactivated users. The auth context now detects the word "banned" in the error and replaces it with a friendly deactivation message.

Account Lifecycle

Account creation

Admins create supervisor and management accounts via the admin panel. The flow:

  1. Admin enters full name, email, phone, and password
  2. A Supabase Auth user is created (via supabaseAdmin.auth.admin.createUser)
  3. A profile row is created with the matching user ID, role, and is_active = true
  4. For supervisors: admin assigns project(s) and floor(s)

Activate / Deactivate flow

Both supervisors and management users are activated/deactivated via the same API endpoint: POST /api/admin/deactivate-supervisor.

StepDeactivateActivate

2. Auth banban_duration = '876000h'ban_duration = 'none'

Deactivation email

On activate/deactivate, the system sends a styled HTML email to the user's registered email address:

  • Navy header bar with "Account Activated" or "Account Deactivated"
  • Personalized greeting with the user's name
  • Role label (Supervisor or Management) with colored status badge (green or red)
  • Contextual message: "You can now log in…" or "Your access has been suspended…"
  • Sent non-blocking — does not delay the toggle response

Deactivated user login behavior

When a deactivated user attempts to log in:

  • Supabase returns a "User is banned" error internally
  • The auth context intercepts this and displays: "Your account has been deactivated. Please contact your administrator."
  • No session is created; the user remains on the login page

Stage Weights

Purpose

Not all construction stages take the same effort. Pre-Tiling (a quick prep stage) is not equivalent to Tiling (a major effort). Stage weights let the admin configure how much each stage contributes to the overall project progress percentage.

How weights work

Weighted Progress = Σ (stage_weight × stage_completion%) / Σ stage_weights
Where stage_completion% = completed activities in stage / total activities in stage × 100
  • Weights are numbers (not percentages) — they represent relative importance
  • Example: Pre-Tiling = 1, Tiling = 5, Post-Tiling = 2 → Tiling counts 5× more than Pre-Tiling
  • If no weights are configured, all stages are equally weighted (fallback to simple average)

Storage

Weights are stored in the app_settings table as a JSON object under the key 'stage_weights':

{
  "Pre-Tiling": 1,
  "Tiling": 5,
  "Post Tiling": 2,
  "Pre Paint Activities": 2,
  "1st Coat Paint": 4,
  "Post First Coat Paint": 1,
  "Second Coat Paint": 3,
  "Post Second Coat Paint": 1,
  "Lobby Flooring": 1
}

The app_settings table uses a simple key (text, PK) / value (jsonb) / updated_at (timestamptz) schema. Reads and writes use upsert with onConflict: 'key'.

Where weights are used

  • Management (Promoter) view — The "Weighted Progress" metric in the insights dashboard uses stage weights to compute a more realistic overall project completion
  • Future: Weights will also feed into the Health Score formula (Section 8) once wired in

Admin configuration

Stage weights are configurable from the admin Settings page. The UI shows each stage with a numeric input for its weight. Changes are saved immediately via the settings repository.

Note Stage weights are currently a global setting (same weights across all projects). Per-project weights may be added in a future version if needed.

Flat completion rule

Core Rule A flat is "complete at stage X" if and only if ALL activities under that stage for that flat have status = completed or completed_delayed. Even if 7 out of 8 activities are done, the flat is NOT complete at that stage.

Calculation method

  1. Fetch all activities for the project
  2. Group by flat_number + stage
  3. For each flat+stage group: check if ALL activities have completed status
  4. Count how many flats have each stage completed
  5. Display as a funnel with 5 horizontal bars

Floor-level breakdown

The same logic is also applied per floor. The promoter can see:

Example Floor 5 (10 flats): Pre-Tiling 10/10, Tiling 7/10, Post-Tiling 3/10, Pre-Paint 0/10, 1st Coat 0/10

Data source

Uses the existing get_dashboard_data heatmap output, which already provides per-flat, per-stage completion counts. Aggregated client-side — no new database function needed.

SPI-Based RAG Status

The Schedule Performance Index (SPI) measures how behind or ahead a floor/project is compared to the plan. This is the same methodology used by large Indian developers (Lodha, Hiranandani, Rustomjee) via their PMC consultants.

Formula

SPI = Actual % ÷ Planned %
Where Planned % = activities whose expected_end ≤ today / total activities
Actual % = activities with status completed or completed_delayed / total activities

RAG thresholds

SPI RangeStatusMeaning
> 0.95GREENOn track or ahead of schedule
0.80 – 0.95YELLOWSlightly behind, recoverable
< 0.80REDSignificantly behind schedule
Example — Floor 5 Floor 5 has 500 total activities.
By today, 300 activities should have been completed (their expected_end date has passed).
Actually, 225 activities are completed.

Planned % = 300/500 = 60%
Actual % = 225/500 = 45%
SPI = 45/60 = 0.75 → RED

This tells the promoter: "Floor 5 is at 75% efficiency — for every 4 days of planned work, only 3 days' worth is getting done."

Why SPI, not projected vs deadline

  • Expected dates are almost always crossed — comparing projected vs expected would show everything as red
  • SPI measures how behind you are right now, not a guess about the future
  • A promoter immediately understands "75% efficiency" — it's actionable
  • The same SPI number works at project level, floor level, or stage level

Floor Projection Logic

This logic answers the promoter's daily question: "When will Floor X finish?"

The approach: Benchmark from completed floors

Instead of guessing future timelines, we use data from floors that are ahead in the pipeline as benchmarks for floors that are behind.

Core Idea Floors that are AHEAD teach us about floors that are BEHIND. It's like being in a bank queue — the people ahead of you ARE the data for how long you'll wait.

Algorithm

For each remaining stage on Floor X:

  1. Has any other floor completed this stage?
    • YES → Average the number of days it took on all completed floors. This is the benchmark.
    • NO → Fall back to counting: look at how many flats completed this stage in the last 14 days. Rate = flats completed / days. Remaining flats / rate = estimated days.
  2. If the stage is currently in progress on Floor X, subtract the days already spent.
  3. Sum up all remaining stage durations.
  4. Projected finish date = Today + total remaining days

Worked example

Project has 15 floors. Today is July 30, 2026.

Current state of the project:

FloorPre-TilingTilingPost-TilingPre-Paint1st Coat
Floor 1DoneDoneDoneDoing—
Floor 2DoneDoneDoing——
Floor 3DoneDoneDoing——
Floor 5DoneDoing———
Floor 10Doing————

Question: When will Floor 5 finish?

Step 1 — Tiling (in progress): Floors 1, 2, 3 finished Tiling in 21, 19, 23 days. Benchmark = 21 days average. Floor 5 started Tiling 8 days ago. Remaining = 21 − 8 = 13 days.

Step 2 — Post-Tiling: Floor 1 finished Post-Tiling in 14 days. Benchmark = 14 days.

Step 3 — Pre-Paint: No floor has finished Pre-Paint yet. Fallback: Floor 1 started 10 days ago, 40/148 flats done. Rate = 4 flats/day. 148/4 = 37 days estimated.

Step 4 — 1st Coat: No data at all. Display as "Insufficient data" or use Pre-Paint estimate as rough proxy.

Result:

Tiling remaining:      13 days  (benchmark: 3 floors)
Post-Tiling:           14 days  (benchmark: 1 floor)
Pre-Paint:             37 days  (rate-based estimate)
1st Coat:              ??       (insufficient data)
────────────────────────────────
Total remaining:       64+ days
Projected finish:      ~October 2, 2026

Why this approach improves over time

  • Early in the project: Few floors have completed stages → most estimates are rate-based (rough)
  • Mid-project: Multiple floors provide benchmarks → projections become accurate
  • Late project: Most stages have been completed on some floor → projections are sharp

The system automatically gets smarter as more data flows in — no manual calibration needed.
